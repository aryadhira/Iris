# 2026-11-13 — P10: a room you can leave and come back to

## What was wrong

The turn was already safe: `streamTurn` uses `context.WithoutCancel`, so hanging up did not stop Hermes.
But the room had no way to *show* that. `GET /api/rooms/{id}` carried no run, and there was no way to attach
to a turn in progress. A phone that came back saw an idle, empty-looking page until a manual reload — which
is why the work looked stopped when it was not.

P10 makes the room, not the POST, the owner of the view.

## The live hub

New package `internal/live`: one hub, one entry per room, a set of subscribers and the partial text of the
turn that is writing.

- `Publish` and `Append` copy the subscriber set under one mutex and use a non-blocking send with a 256-frame
  buffer. A full queue means the reader is gone: it is deleted and its channel closed. The publisher never
  waits for a subscriber.
- `Subscribe` returns the current partial text and registers the channel under the same lock. `Append`
  changes the text and publishes the delta under that lock too. A subscriber therefore sees each character
  exactly once: already in the snapshot, or in a delta published after it attached.
- The POST still streams SSE for compatibility, but it is now only a hub subscriber. Approvals, expiry,
  resolution, system notes, deltas, tools, `done` and errors all leave through the same path, so two devices
  cannot disagree.

`GET /api/rooms/{id}/events` is cookie-authenticated and sends:

1. `snapshot` — `{run, partial, approvals, reminders_due}`;
2. live `delta`, `tool`, `approval`, `approval.resolved`, `note`, `done`;
3. `: keep-alive` every 15 s.

There is no replay log. The snapshot is the resume point. Approvals are capped at the newest 50 in the
snapshot; the transcript still has its own full page.

## Partial persistence rules

- An assistant row is inserted when the turn starts: `state = 'streaming'`, empty body.
- The visible body is written every ~2 s or ~400 characters, whichever comes first.
- The terminal write goes through the existing reply cleaner and artifact resolver: `state = 'done'`.
- On a stream error the partial is kept as `state = 'interrupted'`; a stop keeps what was written.
- Search only returns `state = 'done'`. Export labels a streaming row `(masih ditulis)` and an interrupted
  row `(terputus)`. The speaker button is absent for both, because neither is a final answer.
- A reload mid-turn hides the streaming row from the transcript and renders its body as the growing live
  bubble; the snapshot then replaces it with the exact hub text.

## Restart behaviour

On boot `recoverInterrupted`:

1. marks every `streaming` message `interrupted`;
2. marks `queued`/`running`/`waiting_for_approval`/`stopping` runs `interrupted` with `finished_at`;
3. writes one visible system line per affected room: “balasan sebelumnya terputus — Iris dimulai ulang di
   tengah giliran.”

The partial body is never deleted and never presented as complete. The room payload keeps the interrupted
run, so the header says `terputus` instead of `idle`. A new turn replaces it with normal history.

## Cold-load room payload

`GET /api/rooms` and `GET /api/rooms/{id}` now carry `run: {id, status, started_at, continuation, chain}`.
`run` is present only while the run is live (`queued`, `running`, `waiting_for_approval`, `stopping`) or
visibly `interrupted`; a completed/cancelled/failed run is history and returns `null`. The sidebar dot and
`bekerja · 0:42` therefore work from a cold load with no stream. The list poll is 5 s, so a dot can appear up
to 5 s after a turn starts.

## What a re-entering phone sees now

Before: a page that looked idle until a manual reload. Now, before any new message:

- the header says `bekerja · 1:12` counting from the real start time;
- the partial bubble is already there, marked still writing;
- the tool line names the current tool when one is running;
- pending approvals are rendered as cards from the snapshot;
- `done` arrives live and the final answer replaces the partial without a reload.

## Remaining gaps

- **Hermes' delta cadence is the real limit.** Measured directly against the gateway: a pure text reply
  emits all deltas at once when the model finishes; a preamble before a tool emits right away, then nothing
  during the tool wait. Iris persists and fans out every delta it receives, but it cannot invent text Hermes
  has not sent. During a long tool run the partial is the preamble, not a growing report.
- `menunggu proses` comes from the continuation row, not the run: while a follow-up is merely scheduled
  there is no active run to attach it to. The run carries the attempt index once the follow-up is running.
- If the process dies between a delta and the next 2 s/400-char write, up to that much text is absent from
  the interrupted row. The row is honestly marked `interrupted`; it is not reconstructed.
- Snapshot approvals are capped at 50. A room with more historical receipts gets the rest from
  `GET /api/rooms/{id}/approvals` (the transcript's normal path).
- The sidebar dot is driven by the existing 5 s room-list poll; it is not itself an SSE subscriber.
- The POST stream is kept for compatibility. It is no longer the source of truth, but removing it would
  break older clients, so it remains a second subscriber.

## What this was, and what it was not

Nothing was ever killed: an earlier probe showed the detached turn finishing on its own with the continuation
firing. The defect was that a room had **no way to say it was working** to anyone arriving after the turn started.
The fix makes the state readable — `bekerja · 0:42` from a cold load, the partial answer already on screen, and
the rest arriving without a reload — and keeps the work honest when it fails: a killed turn reads `interrupted`
with what it had written, never a silent completion.

**Known limits:** up to one partial-write window (~2 s / 400 chars) can be lost if the process dies between
deltas; snapshot approvals are capped at 50; sidebar dots follow the existing 5 s room-list poll.

## A second bug found by Boss: a long tool call was killed at 90 s

Screenshot evidence: room "Product Development" at 22:38 showed `idle`, "Hermes tidak mengirim balasan", and a
retry refused with "Room ini masih bekerja". The database told the real story — the run had been `running` and
then `failed`:

```
ERROR "hermes turn failed" error="hermes stream went idle: no data for 1m30s"
run_d043406f… started 22:34:32, failed 22:37:53
```

**Cause.** `defaultIdleTimeout` was 90 seconds. A long tool call (model download, build, voice-engine install,
`sleep`) emits **nothing at all** on the stream while it runs, so the watchdog declared a live turn dead. That
contradicts the product's promise to keep going until the goal is reached — and it failed a real question about
VoxCPM2 in the middle of the answer.

**Fix.** The silence budget is now **10 minutes** (`defaultIdleTimeout`), overridable with
`IRIS_HERMES_IDLE_TIMEOUT` (`25m`, etc.); an unparsable or non-positive value falls back to the default rather
than disabling the watchdog, because a stream that never ends is also a failure, just a quieter one.

**Proof.** A turn that runs `sleep 110; echo SILENT-OK` in the foreground — 110 s of total stream silence, longer
than the old limit — now completes:

```
turn took 116s · run status: completed
reply: "Sudah selesai, Boss. Perintah dijalankan di foreground (tanpa background), menunggu sekitar 110 detik…"
SILENT-OK seen: 2
```

Before this change the same turn died at 90 s and the room was left with no answer.

## A third bug, reported by Boss: leaving the app made a running turn look gone

Symptom: "when i out from apps, then i came back, the long process is gone". The turn was not stopped (the run
kept running), but the app came back to a room showing `idle`.

**Two causes, both real.**

1. **A zombie stream.** Android freezes the tab; the socket dies; `reader.read()` resolves neither a value nor an
   error, so the reconnect loop waited forever on a dead stream. There was no `visibilitychange` handling at all.
   Fixed with (a) a byte-level watchdog: any bytes — including the 15 s heartbeat comment — count as alive, and
   45 s of silence while visible aborts and reconnects; (b) listeners on `visibilitychange` (after >2 s away),
   `pageshow` (bfcache) and `online` that call `resync()`: abort, reset backoff, reconnect, and refresh the
   snapshot. The watchdog interval is injectable (`watchdogMs`) so tests own it instead of hanging the runner.
2. **A turn that started after the page attached was invisible.** The client only learned about a run from a
   snapshot at connect time, so a retry, a continuation, or a turn started from another device left the room
   saying `idle` while the database said `running`. The server now publishes a `run` event the moment the run id
   is known, and the client adopts it.

**Proof, in a real browser against the live instance.**

```
before the fix: a running turn started from another client → chip stayed "idle" (DB said running)
after  the fix: same scenario → bekerja · 0:08, 0:11, 0:14, 0:17, 0:20, 0:23  (clock advancing)
visibility cycle (hidden 3 s → visible) with a live turn → bekerja · 0:28
70 web tests · typecheck clean
```
